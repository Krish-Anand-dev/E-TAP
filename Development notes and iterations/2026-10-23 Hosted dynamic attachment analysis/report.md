# Swap the sandbox for pluggable telemetry providers

A cheaper VM is not the answer. The better path is to change the architecture. Treat "dynamic analysis" as **telemetry from interchangeable providers**: a cloud sandbox API, in-process emulators, the existing local VirtualBox VM, and stored replay recordings. Convert every provider's output into one Sysmon-style event list, then run **one rule engine, written in Sigma rather than Elastic EQL**, over that list. For the hosted edition, the "dynamic" layer has two parts. The first is a set of emulators, one per file type, running in a locked-down container: Speakeasy for PE files and shellcode, box-js for JScript droppers, olevba/ViperMonkey for VBA macros, and headless Playwright for HTML. The second is an optional upload, only with the user's consent, to a free cloud sandbox such as Recorded Future Triage or Hybrid Analysis. The idea of packaging the attachment with code that builds a venv to simulate user interaction cannot work as stated. A Python venv on a Linux container has no Windows, Office or PDF reader to interact with, so it either simulates nothing or runs the payload directly on shared hosting. Reworked as a pre-built emulator image that is run once per job with no network, it becomes the core of the recommendation. The same provider design removes the need for a separate E-TAPlocal build, because the VirtualBox VM becomes one optional plugin. A replay provider gives presentations a repeatable demo that works offline. The main caveat: emulators and free sandboxes are less faithful than a real Windows VM, and every free cloud tier makes uploaded attachments public.

## The venv idea fails, but running emulators in a container works

The idea behind the proposal is sound: bring the analysis environment to the file instead of running a hypervisor. The problem is what a venv can contain. Real "user interaction" with a malicious attachment means opening it in Word, enabling macros, clicking through a PDF, or double-clicking an LNK file on Windows. None of that exists inside a Python virtual environment on Render. If the packaged code instead runs the payload directly, E-TAP is executing untrusted code on shared hosting, which a hosted product must never do. Installing dependencies while a job runs also lets a job that an attacker can influence reach the network and the package index.

The packaging idea does work for emulators. Mandiant's **Speakeasy** is an MIT-licensed Python emulator for Windows programs (user mode and kernel mode) and shellcode. Its report lists API calls with their arguments, file, registry and network activity, and decoded strings ([Google Cloud blog](https://cloud.google.com/blog/topics/threat-intelligence/emulation-of-malicious-shellcode-with-speakeasy/)). It installs with pip and returns its report from code via `get_report()` ([PyPI](https://pypi.org/project/speakeasy-emulator)). **box-js** emulates JScript droppers by faking the WScript.Shell and ADODB.Stream objects, writes `urls.json` and `IOC.json`, and by default returns a fake 404 instead of downloading anything. It is already used in REMnux, Intel Owl and Assemblyline ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fcapacitorset%2Fbox-js); [Assemblyline JsJaws](https://github.com/cybercentrecanada/assemblyline-service-jsjaws)). For macros, ViperMonkey runs the VBA code that fires when a document opens, though its author calls it far from complete ([decalage](https://decalage.info/en/vba_emulation)). **XLMMacroDeobfuscator's last release was 0.2.7 in September 2022** ([pyup](https://pyup.io/packages/pypi/xlmmacrodeobfuscator/)), so treat it as unmaintained. Emulation answers "what would this macro or script try to do", which is the evidence an email triage report needs. It does not show Office windows or click PDF buttons. Playwright can click links and buttons, but only in HTML.

To run this safely, build one container image with every emulator version fixed at build time. Run it as a separate process for each job, with strict CPU, memory and time limits. Give it no network, or a sinkhole that answers every request with fake data. Make the filesystem read-only except `/tmp`, and destroy the container afterwards. Render's plain container is enough for Python and Node emulators, which never run the attachment's own code. If the team later wants stronger isolation, Firecracker-based services such as E2B and Fly Machines give each job its own small VM. Firecracker starts in about **125 ms with under 5 MiB of extra memory** ([fly.io](https://fly.io/learn/)). These services cannot run a Windows VM inside them. Firecracker does not pass the CPU's virtualisation features to the VMs it runs ([codenote](https://codenote.net/en/posts/sandbox-services-japan-region-comparison/)), and Fly staff have said they do not allow a VM inside a VM ([Fly community](https://community.fly.io/t/nested-virtualization-on-fly-io/11778)). Avoid Wine in a container, because it would run the attachment's real code.

## Free cloud sandboxes add real Windows runs, but make uploads public

To run attachments on real Windows without owning a hypervisor, an external sandbox API is the only realistic hosted option. **Recorded Future Triage** fits best. Its v0 API is marked stable and has official Python and Go clients ([tria.ge docs](https://tria.ge/docs/)). Its behaviour report includes the processes launched with their command lines, network connections (including TLS fingerprints and server names), DNS and HTTP requests, signatures tagged with MITRE ATT&CK techniques and YARA matches, memory dumps, and extracted malware configurations ([Triage dynamic report](https://tria.ge/docs/cloud-api/dynamic-report/)). It also has an endpoint that streams raw events and accepts custom YARA rules. **Hybrid Analysis** is the fallback. A free key allows **30 sandbox submissions per day** and 2,000 database requests per hour ([Anomali docs](https://docs.anomali.com/Content/ThreatStream%20Administration/Integrations/Hybrid_Analysis.htm)). It exports JSON, XML, PCAP network captures, MISP and STIX ([HA API](https://www.hybrid-analysis.com/docs/api/v2)).

| Service | Free API? | Limits found | Role for E-TAP |
|---|---|---|---|
| Recorded Future Triage | Researcher accounts | Quota not published | Primary: richest JSON and event stream |
| Hybrid Analysis | Yes | 30 submissions/day | Fallback; network captures help network rules |
| VirusTotal Public | Lookups only | 500/day, 4/min, no product use | Hash lookup only |
| ANY.RUN Community | No API | 60 s VM, 16 MB | Manual demos only |
| Filescan.io / MetaDefender | Yes, limited | 100 MB, public reports | Secondary option |
| CAPE community | Yes, on request | Not published | Report format that capa can read |

Sources: [VirusTotal](https://docs.virustotal.com/reference/public-vs-premium-api), [ANY.RUN plans](https://any.run/plans/), [OPSWAT FAQ](https://www.opswat.com/docs/filescan/faq/what-is-the-difference-between-filescan-io-and-opswat-filescan-c), [CAPEv2](https://github.com/azurda/CAPEv2).

Two limits shape the design. First, **VirusTotal's free API "must not be used in commercial products or services"** ([VirusTotal](https://docs.virustotal.com/reference/public-vs-premium-api)), so use it only to look up hashes. Second, every free tier we found makes submissions public. ANY.RUN Community has no private analyses ([ANY.RUN](https://any.run/plans/)), and Filescan's free reports are public ([OPSWAT](https://www.opswat.com/docs/filescan/faq/what-is-the-difference-between-filescan-io-and-opswat-filescan-c)). An invoice uploaded there can be found by strangers. E-TAP should therefore look up the file's hash first. It should upload only the attachment, never the whole .eml, and only after the user explicitly agrees to send it to a public sandbox. Results take minutes, so uploads must run in the background. Render's free tier sleeps when idle, and `analysis_jobs.py` keeps jobs in memory, so store sandbox task ids in Mongo and resume checking them after a restart. We could not confirm three things from the vendors' own pages: Triage's free quota, its typical turnaround, and whether it enables macros automatically. Test all three before a demo depends on them.

## Moving rules from EQL to Sigma fixes the 36-of-164 problem

The local edition's weak spot is the rules, not the VM. Only 36 of the 164 EQL rules can be evaluated, and the notes show this follows from how the rules are written, not from bugs. Elastic's rules expect fields that only Elastic's own agent records, such as code-signing details and `process.Ext.*`. Sysmon, emulators and sandbox APIs never produce them. The rules are also covered by the **Elastic License v2, which applies to "everything in this repository — rules, code, etc."** ([elastic/detection-rules](https://github.com/elastic/detection-rules)). That licence limits offering the software as a hosted service, so check it before shipping those rules in the hosted edition.

**Sigma** rules work across sources. SigmaHQ publishes more than 3,000 rules under the Detection Rule License 1.1 ([SigmaHQ](https://github.com/SigmaHQ/sigma)). They use Sysmon's field names: `Image`, `CommandLine`, `ParentImage`, `TargetFilename` and `QueryName`. pySigma replaces the old rule converter ([PyPI](https://pypi.org/project/pySigma)). Several engines check rules directly against JSON events without a SIEM. rsigma reads newline-delimited JSON and can rename fields on the way in ([rsigma](https://docs.rs/crate/rsigma/0.10.0)). Zargunlite does the same in pure Python on SQLite, but has not reached version 1.0 ([zargunlite](https://pypi.org/project/zargunlite)). The most useful rules for email attachments flag Office or a PDF reader starting cmd, PowerShell, mshta, wscript, rundll32 or regsvr32. These rules only need the list of processes and their command lines, which every provider supplies in some form. Rules that need loaded DLLs, access to other processes, or code signatures will not carry over. For those, E-TAP should say "can't be checked with this provider" rather than "clean".

Sigma is one of three rule layers. **YARA** checks file contents in malicious documents and droppers. **capa** identifies what a program is capable of and links it to ATT&CK and MBC. capa already reads CAPE, DRAKVUF and VMRay reports ([mandiant/capa](https://github.com/mandiant/capa)), which shows one rule set can work across several sandboxes. When a provider already flags behaviour, such as Triage's ATT&CK-tagged signatures, import its findings as evidence instead of re-deriving them. We found no published converter from Speakeasy output or sandbox reports to a common event format such as ECS or OCSF, so E-TAP must write its own adapters. They are small: four or five event types per provider.

## One provider interface replaces E-TAPlocal and makes demos repeatable

Mature projects split the work into two parts. CAPE and DRAKVUF produce reports; capa and Assemblyline read them and apply rules ([VB2024](https://virusbulletin.com/uploads/pdf/conference/vb2024/papers/Supercharge-your-malware-analysis-workflow.pdf)). For E-TAP, that means a `TelemetryProvider` interface with `submit(file)` and `collect(handle)`. An adapter turns each provider's output into common events, labelled with `event.provider` and with the kinds of data the provider can supply. A single `evaluate(events, rules)` engine runs the rules, and evidence ids such as `dyn.sigma.<rule_id>` feed the existing `evidence.py` ledger. The VirtualBox/Sysmon VM becomes one provider, switched on by an environment variable, so there is one codebase. The rule that E-TAPlocal must stay ahead of E-TAP no longer applies. The sandbox code in `pipeline.py`, `DashboardPage.jsx` and `sandbox.js` becomes shared code that works with any provider.

The **replay provider** is what makes presentations go smoothly. It loads telemetry recorded earlier, either from the team's own VM runs or from public datasets such as EVTX-ATTACK-SAMPLES (about 200 samples sorted by ATT&CK tactic ([GitHub](https://github.com/sbousseaden/EVTX-ATTACK-SAMPLES))). It sends that telemetry through the same adapters and rules. The hosted site then has a reliable demo mode with no quota, no network and no VM, and the same recordings serve as automated tests for every rule. EVTX-ATTACK-SAMPLES is licensed under GPL-3.0, so download the samples when tests run rather than committing them to the repo. Running CAPE or DRAKVUF yourself remains out of reach for now. DRAKVUF needs Intel VT-x with EPT, and running it inside a cloud VM does not work on AWS, GCP, Azure or Hyper-V ([drakvuf-sandbox](https://github.com/CERT-Polska/drakvuf-sandbox)).

## A four-phase plan for a small student team

The phases are ordered by value for the effort and by risk:

1. **Provider interface.** Everything else plugs into it.
2. **Emulators.** They run on the existing Render service at no cost and keep uploaded files private.
3. **Cloud sandbox.** It brings quotas and privacy questions, so it comes after the private options.
4. **Local VM.** It becomes an optional plugin.

| Phase | Work | Outcome |
|---|---|---|
| 1 (2–3 weeks) | Define `TelemetryProvider` and a common event format (Sigma field names plus `provider`). Add a Sigma engine (pySigma/Zargunlite, or rsigma run as a separate process). Build `ReplayProvider` with 10–20 recorded samples. Add a `dynamic` stage to the timeline and `dyn.*` evidence ids. | Hosted demo mode works end to end; rules tested automatically on every change |
| 2 (3–4 weeks) | Build an emulator image with fixed versions: olevba + ViperMonkey, box-js, Speakeasy, Playwright for HTML. No network, resource limits, a fresh temp folder per job. Write adapters to the common format. Pick 50–150 Sigma rules for process starts and file writes (severity medium or higher, status stable or test), plus YARA rules for malicious documents. | Private "dynamic" results for macros, scripts, Windows programs and HTML on Render |
| 3 (2–3 weeks) | Add a Triage adapter with Hybrid Analysis as fallback. Look up the hash before uploading. Ask the user before any public upload. Store task ids in Mongo so checking resumes after a restart. Import the provider's signatures and ATT&CK techniques. | Real Windows runs when the user agrees |
| 4 (ongoing) | Turn VirtualBox/Sysmon into a provider and retire the separate E-TAPlocal codebase. Rewrite the 36 working EQL rules in Sigma. List the fields each rule needs (`requires:`) and show a "can't be checked" state in the UI. Optionally isolate emulators in E2B or Fly microVMs. | One codebase; each provider's coverage shown honestly |

The report should show where each finding came from ("emulated", "cloud sandbox", "recorded demo"). That way non-technical users know how much weight a finding carries, in line with the project's plain-language approach.

## Conclusion

The real problem was never the hypervisor. It was tying the detection rules to one source of telemetry and to one vendor's field names. Once the rules are Sigma and run over a common event list, where the telemetry comes from becomes a setting rather than a separate product. The 36-of-164 limit becomes a field-mapping task instead of a dead end. Three risks remain, and each can be tested: Triage's real free quota and turnaround, how many of the chosen Sigma rules actually fire on emulator output (no published comparison exists), and how well the macro emulators are maintained. One test in phase 2 will answer more than further reading: run the recorded samples and a dozen known malicious documents through every provider and count which rules fire.
